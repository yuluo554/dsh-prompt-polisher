## 二、本次迭代的真正驱动力：**dsh 主版本已经走到 0.2.1**

这是本次迭代最硬的一条，也是唯一有外部时间压力的一条。

| 项 | 实测值 | 命令 |
|---|---|---|
| 本机 dsh | **0.2.0-rc.1** | `dsh --version` |
| npm 上 dsh latest | **0.2.1-rc.2**（2026-10-17T08:36Z） | `npm view @deepseek-ai/dsh dist-tags` |
| 0.2.1 首发 | `0.2.1-alpha.1` = 2026-10-03（插件发布后 **3 天**） | `npm view @deepseek-ai/dsh time` |
| 插件声明的 floor | `dsh.compatibility.dsh = ">=0.2.0-rc.1"` | `package.json` |
| 插件 peerDependencies | 6 个全是**精确 pin**：`@deepseek-ai/cordis@4.0.4`、`dsh-brand@0.2.0-rc.1`、`dsh-client-connection@0.2.0-rc.1`、`dsh-client-ui-plugin-manager@0.2.0-rc.1`、`dsh-client-ui-settings@0.2.0-rc.1`、`dsh-credentials@0.2.0-rc.1` | `package.json` |
| devDependencies | 16 个 `@deepseek-ai/*` 也全是 `0.2.0-rc.1` 精确 pin | `package.json` |

**含义（以下三条是本次诊断最重要的结论，全部源码直读 + semver 实测）**：

1. **`dsh.compatibility.dsh` 是装饰性字段，dsh 从不读它。**
   在 `@deepseek-ai/` 全树（含 dsh 本体与所有子包）grep `manifest.compatibility` / `dsh.compatibility`
   → **0 命中**。真正决定插件能否加载的是 **`peerDependencies`**。

2. **dsh 的校验规则**（`@deepseek-ai/dsh-app-boot/lib/index.js` 的 `evaluatePluginCompatibility()`）：
   - 只校验名字为 `@deepseek-ai/dsh` 或以 `@deepseek-ai/dsh-` 开头的 peer；
   - 判据 = `semver.satisfies(runtimeVersion, range, { includePrerelease: true })`；
   - **不兼容时直接抛错拒绝加载**：
     `if (issue !== void 0 && !issue.exempted) throw new Error(pluginCompatibilityWarning(issue))`
     （注释：*"Only a compatibility conflict denies a row"*）
   - 补救只能靠用户手工 `dsh plugin allow-version`（精确 `包名@版本` + 精确 dsh 版本豁免）。

3. **本插件在 dsh 0.2.1 上会硬失败。** peerDeps 里 5 个 `@deepseek-ai/dsh-*` 全是精确 `0.2.0-rc.1`：

   ```
   runtimeVersion = '0.2.1-rc.2'，dsh 判据 = satisfies(runtime, peerRange, {includePrerelease:true})
   [会被 dsh 校验] @deepseek-ai/dsh-brand                    0.2.0-rc.1  ✗ 不兼容
   [会被 dsh 校验] @deepseek-ai/dsh-client-connection        0.2.0-rc.1  ✗ 不兼容
   [会被 dsh 校验] @deepseek-ai/dsh-client-ui-plugin-manager 0.2.0-rc.1  ✗ 不兼容
   [会被 dsh 校验] @deepseek-ai/dsh-client-ui-settings       0.2.0-rc.1  ✗ 不兼容
   [会被 dsh 校验] @deepseek-ai/dsh-credentials              0.2.0-rc.1  ✗ 不兼容
   [跳过,非 dsh-*] @deepseek-ai/cordis                       4.0.4       ✗ 不兼容（不参与校验）
   ```

   即：**用户升级 dsh 到 0.2.1 后，本插件不是「可能有问题」，而是会被 dsh 直接拒绝加载**。

4. **可用的修法（已实测各候选写法在 5 个 dsh 运行时下的结果）**：

   | peerDependencies 写法 | 0.2.0-rc.1 | 0.2.1-alpha.5 | 0.2.1-rc.2 | 0.2.1 | 0.3.0-rc.1 |
   |---|---|---|---|---|---|
   | `0.2.0-rc.1`（现状） | ✓ | ✗ | ✗ | ✗ | ✗ |
   | `^0.2.0-rc.1` | ✓ | ✓ | ✓ | ✓ | ✗ |
   | `>=0.2.0-rc.1 <0.3.0` | ✓ | ✓ | ✓ | ✓ | ✗ |
   | `>=0.2.0-rc.1`（无上界） | ✓ | ✓ | ✓ | ✓ | ✓ |

   > 注意：dsh 传了 `includePrerelease: true`，所以 `^0.2.0-rc.1` / `>=0.2.0-rc.1`
   > **能**覆盖 `0.2.1-rc.2`（若按普通 semver 规则，预发布不会被任何 range 覆盖——
   > 这个坑在这里被 dsh 自己绕开了，但**必须知道它绕开了**，否则会推出错误结论）。

**我已实测的兼容性（下载 0.2.1-rc.2 的包，直读对比）**：

## 五、本次迭代的目标（建议）

一句话：**让 v0.1.0 在 dsh 0.2.1 上被验证过、并把版本推进到 0.2.0。**

不是因为 0.2.1 有已知破坏（实测没有），而是因为：
1. 用户的 dsh 会自动升级，插件 floor 的实际覆盖范围**未经实测**；
2. peerDeps 精确 pin 在 0.2.1 环境下会产生误导性冲突；
3. v0.1.0 之后 16 天没有任何版本动作，而依赖侧动了 3 次（0.2.1-alpha.1 → rc.2）。

详见 `01-迭代路线.md`。
